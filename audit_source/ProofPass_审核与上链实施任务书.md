# ProofPass：原型审核与区块链升级实施任务书

审阅日期：2026-11-03。

## 1. 结论与交付边界

当前作品是“真实密码学计算 + 会话级模拟业务 + 本地哈希事件链”的教学原型，不是已部署的链上证书系统。保留已有离线 HTML 作为课程必做档，不推翻界面；新增真实测试网版本，让签发登记、状态查询、撤销及交易证据由智能合约提供。

本次完成原始文档核对、HTML 静态审核和核心 JavaScript 逻辑复跑。未部署任何公共测试网合约、未连接用户钱包、未生成真实链上交易。证据文件中的实验使用 Node.js Web Crypto 和 DOM 替身，不是完整浏览器端到端测试。浏览器导航被当前环境策略阻止，不能声称已复测浏览器兼容性。

不要把本任务书称为“完成上链的新版本”；它是后续实现与验收的依据。

## 2. 附件课程要求

依据《学期项目指导书-区块链与智慧校园.docx》第三、六、八节：

- 必做档：独立 HTML，浏览器本地算 SHA-256、记录时间、比较两份文件，无需安装或后端。
- 进阶档：在 Remix 编写三十行以内的合约，部署测试网，再用网页调用；进阶加分最多 5 分。
- 只用当场新建的空钱包和免费水龙头测试币；不接触主网、不用有真实资产的钱包、不在网页输入已有助记词或私钥。
- 方案必须回答节点、权限、纠错、准入、仲裁。真正的访谈、现场证据、含查询日期的链上取证截图和现场问答必须由成员完成，不能由 AI 代造。
- 不需要区块链也可以得到高评价；这不妨碍制作真实链上原型，但必须公平检验它的增量价值。

原型必做档与测试网进阶档应分开发布：离线版继续双击可用；链上版明确需要网络、钱包扩展和 localhost/HTTPS 部署环境，不再宣传“完全离线、无钱包”。

## 3. 已复现的事实与缺口

原始源文件：`ProofPass_跨校证书核验实验室.html`。行号指原 HTML，不是 Files 展开后的引用行号。

### 3.1 正常功能可以保留

正常凭证核验通过；修改被签名字段后签名失败；八种预设案例分别生成预期的教学结论。真实 ECDSA 签名、SHA-256 和前端流程演示不是空壳，但不构成真实机构认证或链上部署。

### 3.2 与区块链直接相关的三个缺口

**链与核验脱节。** `assess()` 从 `state.statuses` 读状态，没有读取账本或任何外部合约。实验中先撤销凭证并追加撤销事件，再仅把 `state.statuses` 改回 valid：核验从 bad 变 pass，而账本仍含撤销事件且一致性检查通过。应改为从固定可信网络、合约、签发方命名空间查询状态；内存只作为带时间和区块号的缓存。

**本地历史可以整体重写。** 只改一条旧记录时 `audit()` 失败；逐条重算摘要及前向引用后检查恢复成功。这说明目前只验证结构自洽，没有独立保存的历史锚点、其他节点或共识。应把这种反例保留为教学挑战，不称为“防篡改链上证明”。

**跨会话证据不成立。** 原型刷新后重新生成机构密钥；导出的 JSON 只有 data、signature、alg，没有长期公钥登记和可信状态定位。新会话使用新公钥验证旧凭证失败。新增凭证导入以及固定的网络/合约配置，才能检验“在另一浏览器独立核验”。

### 3.3 需要修复的其他代码问题

| 问题 | 观察或定位 | 修复要求 |
|---|---|---|
| 持有人自我匹配 | `mainVerify()` 把证书自己的 holderRef 当 expectedHolder；不传 expectedHolder 时 `assess()` 也默认用原 holderRef | 在未做独立认证时显示“未验证”，不得绿色通过；扩展阶段增加持有人挑战签名和身份绑定 |
| JSON 编码不是规范化 | `canonical()` 实际只有 JSON.stringify；重排同一对象键顺序后验签失败 | 为结构化字段采用已测试的规范化方案；若采用固定字节封装，明确其与语义核验的区别 |
| 未知状态标签错误 | status=unknown 的总结果为 wait，但子项文案显示“有效” | 用完整枚举显示“未登记/未知/离线/有效/撤销/过期”，不做默认有效分支 |
| 非预期状态可能放行 | 将状态设置为 unexpected-status 后，当前分支逻辑仍为 pass | 只允许明确的 Active 状态进入通过分支，所有无法识别状态均待复核 |
| 并发追加破坏链 | 两个 appendEvent 同时执行，读取到同一 prevHash 与 index，audit 失败 | 离线版串行写入；链上版依赖交易执行顺序，并处理前端并发、账户 nonce 和失败重试 |
| 存储摘要被截断 | createCert 的事件 meta.digest 只有前 18 个十六进制字符加省略号 | 底层保留完整 32 字节摘要，只在展示层缩写 |
| 演示与业务路径混用 | 挑战函数通过 authOverride/statusOverride 构造教学情境 | 真链核验路径禁止这些覆盖参数；演示测试适配器与真实适配器彻底分开 |

这些结果说明原型不能直接升级宣传为正式系统，并不代表已经攻击了任何现实网站。测试只操作用户提供的本地教学代码。

## 4. 下一版范围：先完成“真链最小闭环”

建议名称：ProofPass Chain——链上存证与撤销的跨校证书核验实验室。

核心路径：机构钱包登记摘要 → 交易成功并记录证据 → 学生导出链下凭证包 → B 校另一浏览器导入并查合约 → 原机构撤销 → B 校重新查询得到撤销状态。

### 4.1 技术选择

第一阶段采用 Solidity + Remix + 公共 EVM 测试网 + 现有前端改造。查阅的 Ethereum 官方网络文档仍把 Sepolia 列为应用开发默认测试网；实际部署前确认网络和免费水龙头可用，网络参数放配置中，不硬编码到业务层。当前 Remix 文档的环境选择名称为 Browser Extension；旧教程常用 Injected Provider。

Remix VM 适合功能调试，但不是公共测试网部署证据。不要仅在 VM 中运行后就写“已部署测试网”。

链上阶段不再把原型每次刷新生成的 P-256 密钥当正式机构凭据：最小版本可用经授权机构钱包发出的登记交易和合约中记录的 msg.sender 证明“哪个获授权地址登记了承诺值”。机构地址与真实机构的对应关系仍须线下准入确认。离线 ECDSA 演示可以独立保留；将来需要离线验签再接长期公钥登记与轮换机制。

### 4.2 链上与链下

链下保存：完整结构化凭证、证书附件、持有人身份/公钥绑定、随机盐、授权出示材料和学校认定规则。

链上最小保存：随机凭证 ID、完整 bytes32 承诺值、签发地址或签发方命名空间、登记时间、有效期、撤销标记。通过事件记录签发与撤销；扩展版记录旧新版本关联。不要将姓名、学号、身份证、证书原文、完整持证人公钥或学生钱包地址作为公开索引。

可采用承诺构造：

`commitment = SHA256( UTF8("ProofPass:v2:") || randomSalt32Bytes || UTF8(canonicalPayload) )`

其中盐是独立的 32 字节密码学随机值，保存在链下凭证包中；canonicalPayload 只包含协议约定的不可变字段，不把交易回执或 commitment 自己放入待哈希对象。结构化载荷包含 schemaVersion；签发地址、链 ID、合约地址可放入明确定义的域隔离上下文，不能由导入文件自行决定哪个合约值得信任。

这是降低小字段猜测风险的设计，不是匿名性证明。链上机构地址、登记时间、凭证索引仍有可关联性。公开授权撤回不可能擦掉已经公开的链上数据，也不能撤回对方已下载的副本。

### 4.3 最小合约职责

建议先做四类操作，而不是 NFT、积分、代币、交易市场：

1. `setIssuer(address,bool)`：受控地配置演示签发方。最小版可由明确披露的管理员控制；共同治理版改为多签控制，不能混称。
2. `issue(bytes32 id, bytes32 commitment, uint64 validUntil)`：仅被授权机构可调用；空 ID、空承诺值、无效期限、同命名空间重复 ID 必须拒绝。
3. `revoke(bytes32 id)`：仅凭证原签发主体依约撤销；不提供重新激活、覆盖原摘要和删除历史的接口。密钥失陷后的紧急处理必须另行设计，不让被禁用密钥任意继续操作。
4. `getRecord(address issuer,bytes32 id)`：只读返回是否存在、原承诺值、登记时间、期限和撤销状态。

优先使用 `(issuerAddress, credentialId)` 命名空间，避免其他签发方用同一个 ID 抢占或覆盖记录。不要只在前端禁用按钮来实现权限。

三十行内的课程基础合约与扩展治理合约分开：基础版先做到讲得清；多签、密钥轮换、原子更正等另作扩展，不用把一大段代码挤成一行来假装满足要求。

### 4.4 前端适配器

定义统一的 LedgerAdapter：issue、getRecord、revoke、getReceipt、getDeploymentInfo。

保留明确标识的 LocalDemoAdapter；新增 TestnetContractAdapter。以后需公平比较时再新增 CentralRegistryAdapter。真实适配器不得静默回退模拟模式；网络失败必须呈现“无法确认链上状态”。

链上界面至少显示：运行模式、链名/chainId、可信合约地址、当前账户/角色、交易哈希、交易状态、区块号、查询时间及所用区块。离线状态不能显示“链上已确认”。

写入完成状态依次区分：待钱包批准、已广播、待打包、已入块成功、确认/最终性状态、失败/拒绝。收到交易哈希不等于执行成功。固定 chainId、可信合约地址及已验证部署，拒绝主网，禁止发送 ETH value。

查询无需让审核员支付链上交易费：通过 eth_call 读取。RPC 服务可能有限流或服务成本，不能因此宣称所有运营成本为零。记录查询时使用的区块高度/哈希、状态和当前时点；缓存过旧或连接中断不能继续显示最新有效。

### 4.5 核验结果必须拆开

建议输出：

- 来源：机构登记权限与交易签发地址是否匹配。
- 完整性：链下包重算的完整承诺值是否匹配链上值。
- 状态：存在、撤销、过期及最新性。
- 持有人：独立身份/挑战证明是否完成，未做则标为未验证。
- 学校认定：规则版本、适用类别、认定结果。

教学 MVP 可以先完成前三项，但不得因此把持有人身份和学校审批也显示为已完成。

## 5. 有趣且有链上意义的演示

### 实验 A：消失的网页，仍在的记录

签发交易成功后导出凭证包，关闭页面，在另一浏览器导入；从既定可信合约重新核验。证明结果不是保存在原页面变量中的绿灯。保证原始凭证包可用；链上摘要不能恢复丢失文件。

### 实验 B：恶意换机构与假合约

使用未授权账户调用 issue，合约拒绝。再把凭证包中的 registryAddress 改成攻击者自己部署的相似合约，核验端因可信部署不匹配拒绝。机构白名单不允许由待验证证书自述。

### 实验 C：当时登记有效，现在已撤销

展示首次核验的区块与状态，再撤销，展示新状态与历史事件。不称旧结果“证明当时事实真实”，只说明当时链上登记状态。误签的追溯处理仍依治理规则。

### 实验 D：纠错不抹史（第二阶段）

把旧凭证撤销，新凭证重新签发，显示可查的旧新关联。最好原子执行；无法原子执行时明确“更正进行中”和中间失败处理。

### 实验 E：有链也会误签

被授权机构故意录入虚构错误信息，技术核验可以通过，但事实仍错误。用这个反例解释源头责任、仲裁和双人复核，而不是说区块链能辨别一切假证。

## 6. 联盟治理与联盟链不能混为一谈

公共测试网上的多机构合约：机构是合约使用者，不是该公共网络的验证节点。

三方中的两方共同批准新增签发机构、移交管理权或紧急处理，是应用层多签治理，不是底层共识。每份普通证书仍由有权签发的机构负责，不让高校投票代替事实确认。

若最终要演示“高校自己维护联盟链节点”，第二阶段可参考 Besu QBFT 官方四验证节点开发网络。在故障模型、网络连通和正确实现等前提下测试节点退出与恢复，并记录日志。四个容器在同一台电脑上，只证明多节点协议实验，不代表四家独立机构真实参与。

普通单管理员合约可以满足真实上链，但治理仍集中；必须如实标注。更复杂系统需要明确成员准入、机构退出、密钥轮换/失陷、误签更正、争议仲裁和权责。

## 7. 如何公平比较区块链的额外价值

原型成本模型：

`T_central = N * t_signed + M_central`

`T_chain = N * t_signed + M_chain`

因此 `T_chain - T_central = M_chain - M_central`。当前模型把单件人工时间设成一样；增加业务量并不会自动让区块链超过中心化。这不是错误公式，但它不能评估多方治理收益，也不是实测结果。

让两种方案保持同一凭证编码、签名/签发主体认证、授权、页面与认定规则，只改变登记/状态后端。分别测人工步骤、误放行/错误拒绝、状态不确定比例、撤销传播、历史可复查性、服务依赖、初始化与维护负担。

中心化基线不能故意设计为完全无权限、无签名、无备份的弱系统。数字签名、追加日志与独立备份也能提升可审计性。区块链是否值得，取决于多方是否需要共享写入/状态记录、能否接受一个共同运营者以及愿意承担多少治理成本。

## 8. 研究材料仍缺什么

1. 真实利益相关方访谈与现行流程材料，而不是模拟案例发生率。
2. 签发方侧证据。申报书的 C 类对象写“签发机构”，访谈提纲实际已改为“带队教师或指导教师”。教师可以提供办理经历，但不能直接证明谁有正式发证/撤销权。应补签发或证书管理人员访谈；若找不到，明确把准入与撤销权限列为尚未验证的假设。
3. 申报书计划的 8 类 × 2 个变体合成任务，以及过期、误签、密钥轮换/失陷等扩展，不等于页面现在的 8 张卡片。
4. 真实的测试网合约地址、部署/签发/撤销回执、带日期截图与复现步骤。
5. 分工与 AI 说明按真实过程更新；不要将这里的建议写成学生已经完成的工作。

## 9. 验收清单

### P0：必须先过

- 离线必做档不损坏；真链模式醒目标识，未部署不得显示已上链。
- 固定可信 chainId/合约；主网写入拒绝；包自带的陌生合约不受信任。
- 正常签发记录有 receipt.status 成功值和区块信息，不能只拿 txHash 当成功。
- 任意未授权账户即使绕过网页直接调用合约也无法签发。
- 同一签发者重复 ID 不能覆盖原记录；其他签发者同 ID 不串记录。
- 另一个浏览器可导入包，使用链上状态核验，不依赖原会话密钥。
- 改 payload 或盐，承诺不匹配；等价 JSON 字段顺序变化按约定编码处理。
- 非原签发者不能撤销；合法撤销后刷新/换浏览器也不能重新变有效。
- 未登记、未知、意外状态、RPC 超时、错误网络、错误地址都不默认通过。
- 持有人未认证时不显示“绑定通过”；学校规则不等同链上有效性。
- 合约状态、调用参数、事件中没有真实身份原文。
- 团队亲自拍摄部署、查询与撤销截图，记录查询日期。

### P1：闭环完成后再做

- 旧新版本关联；必要时原子撤销与替换。
- 多签管理准入/紧急操作；普通发证责任保持明确。
- 机构公钥/地址轮换与历史授权记录；停用新签发权限不自动抹掉旧发证历史。
- 持有人使用与凭证绑定的密钥签名出示：随机 challenge、目标学校、用途、截止时间和协议域；接收端检查挑战唯一并防重放。控制某把密钥不自动等于现实学生身份，绑定必须先由可信流程确认。
- 核验报告导出，包含状态、区块信息、规则版本和未完成检查项。
- 使用完全相同前端与任务比较中心化和链上后端。

### P2：选做

Besu 多节点实验、批量 Merkle 存证或选择性披露。没有前述闭环前不要开展。去中心化存储、NFT、通证或零知识证明不作为当前必要功能。

## 10. 可直接交给实现者的总任务

> 保留原离线教学 HTML，新增明确标识的测试网模式。首先修复未知状态误显示、异常状态默认通过、假持有人匹配、字段编码与并发事件写入问题。实现独立 LedgerAdapter，将真链登记、查询、撤销和回执读取与模拟适配器分离。以受授权机构钱包发出的交易登记完整承诺值，合约内执行权限；仅使用新空钱包、免费测试币及允许的测试网。凭证原文与随机盐留在链下，支持凭证包导出及另一浏览器导入；核验端使用固定可信网络和合约，不信任文件自报地址。先通过 P0 验收，再做版本更正、多签治理与持有人防重放。不伪造地址、交易哈希、部署截图、真实访谈或测试结果。交付源码、合约 ABI、编译配置、实际部署配置、测试用例与真实运行日志，并明确哪些功能尚未实现。
